# README_CHANGELOG

## Финальная стабилизация текущего контура

Проект остается монолитным Flask-приложением: `app.py`, `models.py`, `forms.py`, `views.py`, `templates/`, `static/css/app.css`, `migrations/versions/`.

Большой производственный модуль не затрагивался: склад комплектующих, полуфабрикаты, спецификации, списание, сотрудники, смены, HR, участки и станки не добавлялись.

## Продажи и отгрузка

Продажа ведется через заказ. Договор создается только из карточки заказа маршрутом `/orders/<id>/contract/new`.

Прямой маршрут `/contracts/new` заблокирован: он показывает сообщение и перенаправляет на список заказов. Один заказ может иметь максимум один договор, это защищено серверной логикой и уникальным индексом `sales_contract.order_id`.

Правильное разделение статусов:

- выдача документов = юридическая продажа;
- физическая отгрузка клиенту = отдельное событие.

При выдаче документов через `/orders/<id>/issue-documents`:

- `CustomerOrder.status = sold_not_shipped`;
- `CustomerOrder.documents_issued = True`;
- `Trailer.status = SOLD`;
- `SalesContract.is_paid = True`;
- `SalesContract.is_shipped = False`.

При физической отгрузке через `/orders/<id>/ship`:

- `CustomerOrder.status = shipped`;
- `CustomerOrder.is_shipped = True`;
- `Trailer.lifecycle_status = customer_shipped`;
- `SalesContract.is_shipped = True`.

`SOLD` означает юридически продан. `customer_shipped` означает физически отгружен клиенту.

В обычной форме заказа поля `documents_issued` и `is_shipped` не редактируются. Эти состояния меняются только специальными маршрутами.

После юридической продажи документальный статус нельзя откатить кнопками "счёт отправлен", "договор готов" или "документы готовы". Старый совместимый POST `/orders/<id>/documents-issued` не меняет данные и перенаправляет в карточку заказа.

## Договоры

Менеджер может создать/редактировать договор только по своему заказу и только до выдачи документов. После выдачи документов редактирование и удаление для менеджера закрыто.

Логист и производство не имеют доступа к созданию, редактированию и удалению договоров. Директор открывает список, печать и PDF в режиме просмотра. Админ имеет полный доступ.

SigeX-подписание доступно только ролям, которые могут управлять договором до выдачи документов. Если WeasyPrint не установлен, обычный `/contracts/<id>/pdf` перенаправляет на HTML-печать, а SIGEX PDF endpoint отвечает управляемым `503` с JSON-ошибкой вместо stacktrace.

Печатная HTML-форма договора приведена к A4: `@page`, фиксированная ширина печатной области, нормальные поля и запрет плохих разрывов таблиц/подписей.

## Склад менеджера и подбор

Вкладка "Мой склад" по умолчанию показывает только свободные к продаже прицепы на складе менеджера.

Группы фильтра склада:

- свободные к продаже;
- забронированные;
- проданы, но не отгружены;
- в пути;
- выпущены без VIN;
- готовы на производственном складе;
- отгружены клиенту;
- все.

Группа "Проданы, но не отгружены" включает `Trailer.status = SOLD` и `Trailer.lifecycle_status != customer_shipped`. Такие прицепы нельзя продать повторно, но их видно для контроля отгрузки.

Подбор прицепа в заказе фильтруется по модели, складу продажи и источнику исполнения. Не показываются физически отгруженные, занятые другим активным заказом и конфликтующие с активным перемещением прицепы.

Добавлены API:

- `/api/customers/search`;
- `/api/order-availability`;
- `/api/movement-trailers/search`.

## Логистика

Логист может перемещать:

- свободные прицепы;
- забронированные;
- проданные юридически, но еще не отгруженные клиенту.

Логист не может выбрать прицеп с `lifecycle_status = customer_shipped` и прицеп, уже находящийся в активном перемещении.

В рабочем месте логиста блок "Готово на складе выпуска" показывает только прицепы, которые реально нужно отправить со склада выпуска: `IN_STOCK`/`RESERVED`, задан склад назначения, склад назначения отличается от склада выпуска, нет активного перемещения. `SOLD` не попадает в этот блок. Для юридически проданных, но физически не отгруженных прицепов есть отдельный блок "Продано, не отгружено клиенту".

Добавлено групповое перемещение:

- `/stock-movements/batch/new`;
- несколько `StockMovement` создаются с общим `batch_key`;
- у прицепов меняется `lifecycle_status = in_transit`;
- `SOLD` не затирается при складском перемещении юридически проданного прицепа.

## Производство и пополнение склада

Сценарии поддерживаются отдельно:

- `CUSTOMER_ORDER` - производство под клиентский заказ;
- `STOCK_REPLENISHMENT` - производство на складское наличие.

Производственник видит тип потребности, склад назначения, количество, срок и комментарии, но не видит коммерческие суммы.

В карточке производства выводятся комментарии из заявки, строки, потребности, заказа и производственного комментария.

Создание строки производства из потребности защищено от дублей: одна активная потребность не может быть привязана к двум активным строкам производства.

## Диалоги и заявки

Добавлен раздел `/conversations` для входящих обращений. Webhook-сообщения группируются по каналу и `external_chat_id`, затем по телефону. Повторный `external_message_id` не создает дубль сообщения.

Менеджер видит свои, неназначенные и складские диалоги. Production/logistics не имеют доступа к коммерческим диалогам.

## Защита от дублей

Добавлена модель `IdempotencyKey` и серверная idempotency-защита для ключевых POST-действий:

- создание заказа;
- создание клиента;
- создание договора;
- выдача документов;
- добавление/отмена оплаты;
- создание потребности;
- создание и редактирование производственной заявки;
- выпуск единицы;
- присвоение VIN;
- создание одиночного и группового перемещения;
- приемка перемещения;
- физическая отгрузка клиенту.

Фронтовая блокировка submit-кнопок оставлена как вспомогательная мера, но основной контроль выполняется сервером.

## Панель директора

Главная панель директора показывает управленческую ситуацию, а не справочник с нулевыми строками:

- выручка и продажи за день/неделю/месяц;
- свободно к продаже;
- резерв;
- продано, но не отгружено;
- в пути;
- активное производство;
- выпущено без VIN;
- готово с VIN;
- проблемные зоны;
- ближайшие отгрузки;
- активные перемещения.

Фильтры: период, склад/филиал, статус. Подробности вынесены в `/director/reports` и разделы:

- продажи;
- склад;
- производство;
- перемещения;
- проблемные заказы;
- отгрузки;
- финансовая сводка.

Нулевые строки остатков скрываются по умолчанию; для них есть переключатель.

## Быстрая отправка SOLD и закрепление будущих VIN

- Быстрая отправка логиста разрешает `Trailer.status = SOLD`, если прицеп ещё не `customer_shipped`.
- `SOLD` можно перемещать только до физической выдачи клиенту; при отправке `status` остаётся `SOLD`, а `lifecycle_status` становится `in_transit`.
- `customer_shipped` не отображается в рабочих списках логиста и недоступен для перемещения.
- `ProducedUnit` получил связь с заказом через `order_id`.
- В карточке заказа добавлено закрепление выпущенной единицы без VIN под заказ.
- В карточке заказа добавлено закрепление готового VIN на производственном складе под заказ.
- После присвоения VIN закреплённой `ProducedUnit` созданный `Trailer` автоматически связывается с заказом.
- Статус закреплённого прицепа после VIN: `RESERVED`, если документы ещё не выданы, и `SOLD`, если заказ уже юридически продан.
- Если готовый VIN закрепляется под заказ и склад выдачи отличается, создаётся перемещение под заказ без дублей.

## Проверка перед сервером

Команды:

```powershell
$env:FLASK_APP = "app:create_app"
python -m compileall .
flask routes
flask db current
flask db upgrade
```

Ручные сценарии:

1. Продажа из наличия: заказ -> резерв VIN -> оплата -> договор из заказа -> выдача документов -> `sold_not_shipped` + `SOLD` -> физическая отгрузка -> `shipped` + `customer_shipped`.
2. Продажа прицепа в пути: закрепить входящее перемещение за заказом -> принять -> документы -> физическая отгрузка.
3. Производство под клиента: потребность -> производство -> выпуск без VIN -> VIN -> перемещение -> приемка -> документы -> отгрузка.
4. Пополнение склада: заявка на склад -> производство -> VIN -> отправка -> приемка -> `IN_STOCK` на складе назначения.
5. Двойной POST: повторное создание заказа, договора, оплаты, выпуска, VIN, перемещения и отгрузки не должно создавать дубль.
6. Групповое перемещение: общий `batch_key`, прицепы в пути, customer_shipped недоступен к выбору.
7. Печать договора: HTML-форма печатается в A4 через Ctrl+P / Save as PDF.
8. Права: production/logistics не открывают заказы, клиентов, договоры и диалоги; менеджер работает только со своим складом; директор смотрит панель и отчеты.
