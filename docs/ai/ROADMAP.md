# Важно: новый статус roadmap

С 03.06.2026 этот roadmap больше не является планом развития Trailers как самостоятельной ERP-платформы.

Теперь этот файл используется как:

1. исторический контекст;
2. карта текущих проблем legacy Trailers;
3. источник бизнес-доменов для переноса в Flexity;
4. список зон, которые нужно учитывать при проектировании `industry_trailers`.

Новая целевая архитектура:

```text
Flexity = основная ERP-платформа
Trailers Flask = legacy/reference
industry_trailers = будущий отраслевой пакет Flexity
```

Перед выполнением любого пункта roadmap нужно определить:

```text
1. Это критичная поддержка текущего Flask Trailers?
2. Это нужно перенести во Flexity как универсальный модуль?
3. Это относится к отраслевому пакету industry_trailers?
4. Это устаревший пункт, который больше не нужно делать в Trailers?
```

Новые универсальные модули не добавляются в Trailers.

Универсальные функции — CRM, финансы, документы, подписки, AI, налоговый, HR, payroll, склад, производство — проектируются во Flexity.

Trailers используется как источник логики по:

* VIN;
* ОТТС;
* комплектациям;
* заказам прицепов;
* производству прицепов;
* складу готовых прицепов;
* документам на прицепы;
* отраслевой себестоимости.
# Roadmap — Trailers

Дата обновления: 2026-06-03

## Главная цель на текущий этап

Сначала стабилизировать текущий контур Trailers, затем развивать модули управленческого учета по этапам. Проект уже большой, поэтому новые функции нельзя добавлять поверх хаоса: сначала контекст, миграции, роли, статусы и сценарии проверки.

## Сейчас делаем

### Этап 0 — техническая стабилизация Cursor/Git/контекста

Цель: остановить drift и вернуть управляемость разработки.

Критерии готовности:

- [ ] Заполнены `docs/ai/PROJECT_CONTEXT.md`, `ROADMAP.md`, `DO_NOT_TOUCH.md`.
- [ ] Создан `.cursorignore`, чтобы Cursor не индексировал venv, backup, db, pyc, diff/zip/xlsx.
- [ ] Создан `.gitattributes` или решен вопрос `LF/CRLF`, чтобы Git не показывал десятки ложных изменений.
- [ ] Проверено `git diff --ignore-cr-at-eol --stat`.
- [ ] Перед кодом всегда используется research-first workflow.

### Этап 1 — ревизия текущего состояния проекта

Цель: понять, что реально работает, что слетело, что нужно чинить первым.

Критерии готовности:

- [ ] Проверена миграционная версия локальной базы и migration head.
- [ ] Проверено, какая база используется локально: `trailers.db` или `instance/trailers.db`.
- [ ] Запущены `python -m compileall .`, `flask routes`, `flask db current`.
- [ ] Проверены основные роли: admin, director, manager, production, logistics, warehouse.
- [ ] Создан audit report в `docs/ai/research/`.
- [ ] Составлен список багов/косяков с приоритетом.

### Этап 2 — стабилизация CRM + заказы + VIN

Цель: закрепить текущий коммерческий цикл без регрессий.

Критерии готовности:

- [ ] Многострочные заказы работают через `CustomerOrderLine`.
- [ ] VIN привязывается к правильной строке заказа.
- [ ] Реализация не подставляет чужой VIN.
- [ ] `SOLD` и `customer_shipped` не смешиваются.
- [ ] Менеджерские, логистические и директорские сценарии проверены вручную.

### Этап 3 — производство + пополнение склада + ТМЦ

Цель: стабилизировать производственный цикл и складские остатки.

Критерии готовности:

- [ ] Производство под клиента и на склад разделены.
- [ ] Выпуск без VIN, присвоение VIN и отправка на склад работают.
- [ ] BOM-списание и возврат материалов при удалении выпуска проверены.
- [ ] Дефицит ТМЦ показывает реальные потребности.
- [ ] Кладовщик/закупщик работает в отдельном контуре.

### Этап 4 — финансы и управленческая отчетность

Цель: расширить финансовый модуль без смешивания с юридической реализацией и налогами.

Критерии готовности:

- [ ] Описан текущий денежный контур: заказы, оплаты, договоры, реализации.
- [ ] Разделены управленческая выручка, юридическая реализация, кассовые поступления, задолженность.
- [ ] Определены отчеты директора.
- [ ] Создан ADR перед изменением финансовой модели.

### Этап 5 — налоговый модуль

Цель: спроектировать налоговый контур отдельно от CRM и управленческих отчетов.

Критерии готовности:

- [ ] Описаны налоговые события: договор, оплата, реализация, отгрузка, возврат/отмена.
- [ ] Описаны источники данных для налоговых отчетов.
- [ ] Определено, какие документы юридически значимы.
- [ ] Создан ADR.
- [ ] Без ADR не менять `SalesRealization`, `SalesContract`, `OrderPayment`, статусы документов и отгрузки.

### Этап 6 — кадры / HR / производство по сотрудникам

Цель: развить кадровый и производственный учет без поломки текущих смен.

Критерии готовности:

- [ ] Описаны сотрудники, должности, участки, смены, выработка, начисления.
- [ ] Связь HR с производственными сменами отделена от CRM.
- [ ] Роли `laser_operator` и `bending_operator` проверены.

### Этап 7 — AI-сотрудники

Цель: добавить AI-сотрудников как управляемый слой, а не хаотичный автопилот.

Критерии готовности:

- [ ] AI-сотрудник имеет роль, права, журнал действий и human approval для опасных операций.
- [ ] AI не может менять деньги, документы, VIN, миграции, production config без approval.
- [ ] AI-ответы клиентам проходят через очередь/статус, а не напрямую в production.
- [ ] Есть журнал: кто/что/когда предложил или выполнил.

## Не делаем сейчас

- Не строим налоговый модуль до стабилизации заказов/реализаций/финансов.
- Не внедряем AI-сотрудников с правом менять данные без approval.
- Не переписываем проект на другой фреймворк.
- Не выносим микросервисы.
- Не делаем широкий рефакторинг `views.py` без отдельной стратегии.
- Не меняем миграции и схему базы “по ходу дела”.
- Не чистим backup/db/venv файлы без отдельного safety checkpoint.
