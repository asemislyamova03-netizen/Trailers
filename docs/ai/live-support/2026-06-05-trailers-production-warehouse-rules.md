## 1. Назначение документа

Этот документ фиксирует **каноническое значение** производственного склада в Trailers. Он создан после повторяющихся ошибок агентов (Cursor/Codex), которые трактовали флаг `is_production` как признак «склад только для производства» и исключали такие склады из продаж, заказов, остатков и перемещений.

**Цель:** любой агент или разработчик перед изменением складской, производственной или продажной логики обязан свериться с этим документом.

---

## 2. Что такое производственный склад

### 2.1. Базовое правило

**Производственный склад — это всё ещё склад.**

В модели `Warehouse` флаг `is_production` (в UI — «производственный склад») **не отменяет** статус склада как полноценного участника складского и коммерческого контура.

| Аспект | Поведение для `is_production=True` |
|--------|-------------------------------------|
| Продажи | Участвует |
| Остатки / availability | Участвует |
| CRM / заказы | Участвует |
| Резервирование | Участвует |
| Перемещения между складами | Участвует |
| Производственная зона | **Дополнительно** присутствует |

### 2.2. Что означает `is_production`

Флаг означает только одно: **на этом складе есть производственная площадка** (production area), внутри которой ведётся учёт производственных зон и выпуска.

`is_production` **не означает:**

- «склад нельзя выбирать в заказе»;
- «с этого склада нельзя продавать»;
- «прицепы на этом складе не видны менеджеру»;
- «перемещения с/на этот склад запрещены»;
- «остатки этого склада не участвуют в availability».

---

## 3. Внутренние производственные зоны

Производственная площадка склада может включать зоны хранения и учёта (через `WarehouseStorageArea` и связанную логику):

| Зона | Русское название | Содержимое |
|------|------------------|------------|
| Components | Комплектующие | Материалы и детали для сборки |
| Semi-finished goods | Полуфабрикаты | Промежуточные изделия |
| Work in progress | Незавершённое производство | Единицы в процессе сборки |
| Finished goods | Готовая продукция | Выпущенные прицепы, готовые к продаже/резерву/перемещению |

Зоны — **внутренняя организация** производственного склада. Они не заменяют и не отменяют участие склада в общем складском и продажном контуре.

## 4. Логика готовой продукции (finished goods)

### 4.1. Выпуск

После завершения производственного цикла **готовый прицеп** появляется в зоне **готовой продукции** производственного склада (finished goods area of the production warehouse).

Типичный путь:

1. Производственная заявка / выпуск (`ProductionRequest`, `ProducedUnit`).
2. Присвоение VIN (если требуется для данного изделия).
3. Размещение в зоне готовой продукции на производственном складе.
4. Прицеп становится доступен в общем складском и коммерческом контуре **этого же склада**.

### 4.2. После выпуска (release)

Выпущенный готовый прицеп на производственном складе может:

| Действие | Разрешено |
|----------|-----------|
| Продажа с этого склада | Да |
| Резервирование под заказ (`CustomerOrder` / `CustomerOrderLine`) | Да |
| Перемещение на другой торговый/складской склад (`StockMovement`) | Да |
| Хранение как свободный остаток (available stock) | Да |

Производственный склад — **валидный источник** готовой продукции для всех этих сценариев наравне с обычными торговыми складами.

## 5. Участие склада в продажах и перемещениях

### 5.1. Продажи и CRM

- Менеджер может подбирать прицепы с производственного склада.
- Заказы могут ссылаться на прицепы/остатки производственного склада.
- Availability и отчёты по остаткам **должны включать** производственные склады, если бизнес-процесс это предполагает (а по умолчанию — предполагает).

### 5.2. Перемещения

- Перемещение **с** производственного склада (например, готовая продукция → торговый филиал) — штатный сценарий.
- Перемещение **на** производственный склад — штатный сценарий (если процесс это допускает).
- Фильтры UI и запросы к БД **не должны** по умолчанию исключать `is_production=True` из списков складов для продаж и перемещений.

### 5.3. Историческая ошибка агентов

Ранее агенты вносили изменения вида:

- `WHERE is_production = 0` в выборках для продаж/заказов;
- скрытие производственного склада в dropdown выбора склада менеджера;
- исключение production warehouse из stock availability.

**Такие изменения считаются регрессией** и должны откатываться или не вноситься.

## 6. Правила VIN и прицепов (trailers)

### 6.1. Прицепы (trailers)

Готовые прицепы — сущности с VIN-жизненным циклом:

- `Trailer`
- `VinRegistry` / `VinRegistryEvent`
- `ProducedUnit` (связь выпуска с физической единицей)
- `trailer_id` в строках заказа и связанных документах

Для **настоящих прицепов** эти сущности обязательны в соответствующих workflow.

### 6.2. Комплектующие и товары — не прицепы

**Комплектующие (components) и товары (goods) — это не прицепы.**

Для номенклатуры типа COMPONENT / GOODS (и аналогичных не-trailer позиций) **запрещено требовать**:

| Поле / сущность | Для components/goods |
|-----------------|----------------------|
| VIN | Не требуется |
| `trailer_id` | Не требуется |
| `vin_registry` | Не требуется |
| `produced_unit` | Не требуется |

Попытка протащить комплектующие через trailer/VIN workflow — **временный обходной путь** (см. P1-A discovery), а не целевая модель.

### 6.3. Разделение в коде и UI

При реализации guards, валидаций и фильтров агент обязан различать:

- **Trailer line** — VIN, produced_unit, trailer_id уместны.
- **Goods/component line** — только номенклатура, количество, склад, остатки ТМЦ; без VIN-контура.

## 7. Исключение: товары и комплектующие

### 7.1. Текущее состояние

Полноценный контур **продажи товаров и комплектующих** (отдельно от прицепов) в Trailers **ещё не реализован**. Менеджеры иногда вводили не-прицепные позиции через trailer/order workflow — это зафиксировано в P1-A discovery.

### 7.2. Целевое направление

Нужен **будущий goods/component sales flow**:

- отдельные типы строк заказа (GOODS, COMPONENT, SERVICE);
- продажа без VIN и без `ProducedUnit`;
- учёт через `Item`, `InventoryBalance`, складские операции ТМЦ;
- без привязки к `Trailer` и `VinRegistry`.

### 7.3. Что нельзя делать сейчас

- Не расширять требование VIN на все позиции склада «потому что это production warehouse».
- Не считать, что всё на производственном складе — прицепы с VIN.
- Не блокировать продажи components/goods из-за отсутствия VIN — нужен отдельный flow, а не обход через placeholder-VIN.

## 8. Запрещённые допущения для агентов (Cursor / Codex)

Перед любым PR или hotfix агент **не должен** исходить из следующих ложных предпосылок:

| № | Запрещённое допущение | Правильная интерпретация |
|---|----------------------|--------------------------|
| 1 | «Production warehouse ≠ sales warehouse» | Production warehouse **является** sales warehouse |
| 2 | «`is_production` исключает склад из заказов» | Флаг только маркирует наличие производственной зоны |
| 3 | «С production warehouse нельзя продавать» | Можно продавать готовую продукцию после release |
| 4 | «Availability не считает production warehouses» | Должен считать, если иное не задокументировано отдельным ADR |
| 5 | «Перемещения только между торговыми складами» | Production warehouse участвует в transfers |
| 6 | «Всё на production warehouse требует VIN» | Только прицепы; components/goods — нет |
| 7 | «Components = trailers с placeholder VIN» | Components — отдельная номенклатура без VIN-контура |
| 8 | «Упростим: уберём production из sales queries» | Регрессия; запрещено без explicit user approval и ADR |

### 8.1. Обязательная проверка перед изменением кода

Если патч затрагивает:

- `Warehouse`, `is_production`;
- фильтры складов в `views.py`, forms, templates;
- availability, stock, reservations;
- production release → sales handoff;

агент обязан:

1. Прочитать этот документ и секцию в `PROJECT_CONTEXT.md`.
2. Убедиться, что production warehouses **не исключены** из затронутого контура.
3. Разделить логику trailers vs goods/components.
4. Не менять production data, не деплоить, не перезапускать сервис без отдельного approval.

## 9. Последствия для будущей реализации

### 9.1. Flexity / industry_trailers

При переносе в Flexity (`industry_trailers`):

- `is_production` остаётся **атрибутом склада**, а не типом «непродаваемого» склада.
- Production areas маппятся на зоны хранения / workflow steps внутри tenant warehouse.
- Finished goods release должен оставлять единицу в том же warehouse entity с полным участием в sales/stock.

### 9.2. Планируемые доработки Trailers (legacy)

| Направление | Описание |
|-------------|----------|
| P1 — Goods/component sales | Отдельный order line type и UI без VIN |
| Guards | Warehouse guards не должны трактовать `is_production` как exclusion flag |
| UI | Dropdown складов для менеджера включает production warehouses |
| Reports | Остатки и availability агрегируют production + trade warehouses по бизнес-правилам роли |
| Production release | После release прицеп в finished goods zone **и** в общем stock контуре |

### 9.3. Критерий приёмки для складских изменений

Изменение считается корректным, если:

1. Production warehouse виден и доступен в sales/order/stock flows (если роль это допускает).
2. Выпущенный прицеп на production warehouse можно зарезервировать, продать или переместить.
3. Components/goods не попадают под обязательный VIN/`produced_unit`.
4. Нет новых `WHERE NOT is_production` (или эквивалентов) в коммерческих запросах без ADR.

## 10. Краткая шпаргалка

```
Производственный склад = обычный склад + производственная зона.

is_production  →  есть production area (комплектующие, полуфабрикаты, WIP, готовая продукция)
is_production  ↛  исключение из продаж / заказов / остатков / перемещений

Готовый прицеп после release  →  finished goods zone  →  sell | reserve | transfer | stock

Components/goods  →  НЕ прицепы  →  без VIN, trailer_id, vin_registry, produced_unit
                 →  нужен будущий goods/component sales flow

Агентам: НЕ убирать production warehouses из sales/order/stock logic снова.
```
