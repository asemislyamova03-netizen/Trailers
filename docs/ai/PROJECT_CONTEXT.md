# Project Context — Trailers

Дата первичного AI-аудита: 2026-06-03
Проект: `Trailers`
Рабочая ветка из архива: `crm-roles-production-logistics`

## Название проекта

Trailers — внутренняя система управленческого учета производства, продаж, склада и документооборота по прицепам.

## Что делает проект

Проект предназначен для управления полным циклом работы компании, которая производит и продает прицепы. Уже реализован большой контур CRM: клиенты, заявки, диалоги, заказы, договоры, оплаты, выдача документов, физическая отгрузка, VIN-реестр, перемещения, производство, пополнение склада, ТМЦ, поставщики, планы поступлений и директорские отчеты.

Целевая версия должна стать управленческой ERP/CRM-системой для производства и продажи прицепов: продажи, производство, закупки, склад, финансы, кадры, налоговый контур, интеграции и AI-сотрудники. Проект нельзя вести как одноразовый прототип: почти каждое изменение затрагивает бизнес-процессы, роли, складские остатки, документы, деньги или историю операций.

## Главная цель проекта

Стабилизировать существующую систему и продолжать развитие поэтапно, без поломки уже работающих контуров:

1. CRM и сделки.
2. Заказы и многострочные позиции.
3. VIN-жизненный цикл.
4. Производство под клиента и на склад.
5. Склад готовой продукции и ТМЦ.
6. Договоры, оплаты, реализации и отгрузки.
7. Директорская управленческая отчетность.
8. Будущие модули: финансы, налоговый учет, кадры/HR, AI-сотрудники, расширенные интеграции.

## Как запустить проект локально

Требует проверки в реальной среде. Базовый предполагаемый запуск:

```bash
python -m venv .venv
source .venv/bin/activate  # Mac/Linux
# или Windows PowerShell:
# .venv\Scripts\Activate.ps1

pip install -r requirements.txt
set FLASK_APP=app:create_app  # Windows CMD
# или PowerShell:
# $env:FLASK_APP = "app:create_app"
# или Mac/Linux:
# export FLASK_APP=app:create_app

flask run
```

Важно: архив содержит `venv_trailers/`, но его нельзя считать переносимым окружением. Лучше создать новый `.venv` локально.

## Важные бизнес-ограничения

1. Юридическая продажа и физическая отгрузка — разные события.
2. `Trailer.status = SOLD` не означает, что прицеп физически выдан клиенту.
3. Физическая выдача клиенту фиксируется через `lifecycle_status = customer_shipped`.
4. Многострочные заказы должны работать по `CustomerOrderLine`, а не только через поля шапки заказа.
5. VIN нельзя присваивать повторно, если он уже есть у прицепа.
6. Выдача документов и реализация должны проверять VIN по строкам заказа.
7. Production/logistics не должны видеть коммерческие данные, если это не предусмотрено ролью.
8. Менеджер ведет сделку; склад менеджера не должен автоматически запрещать работу с техникой другого склада, если бизнес-процесс это разрешает.
9. Производство под клиента и производство на склад — разные сценарии.
10. Списание ТМЦ по BOM должно быть обратимым при удалении выпуска.
11. Двойной POST не должен создавать дубли заказов, договоров, оплат, VIN, перемещений, выпусков и реализаций.
12. Налоговый модуль должен проектироваться отдельно: он влияет на документы, реализации, оплаты, отчетность и юридические статусы.

## Production Warehouse Rule

Производственный склад (`Warehouse.is_production`, «производственный склад») — это **обычный склад**, у которого дополнительно есть производственная зона. Флаг `is_production` **не исключает** склад из продаж, остатков, CRM, заказов, доступности и перемещений.

`is_production` означает только то, что на складе есть производственная площадка с зонами: комплектующие, полуфабрикаты, незавершённое производство, готовая продукция. После выпуска готовый прицеп попадает в зону готовой продукции этого же склада и далее может продаваться, резервироваться под заказ, перемещаться на другой склад или оставаться свободным остатком.

Комплектующие и товары — **не прицепы**: для них не требуются VIN, `trailer_id`, `vin_registry`, `produced_unit`; нужен отдельный будущий контур продажи товаров/комплектующих. Агентам Cursor/Codex **запрещено** снова исключать производственные склады из логики продаж, заказов и складских остатков.

Подробно: `docs/ai/live-support/2026-06-05-trailers-production-warehouse-rules.md`.

## Текущие технические риски

1. `views.py` слишком большой: около 15 000 строк и 177 маршрутов. Любые изменения в нем нужно делать точечно.
2. `models.py` большой: около 1 900 строк и 66 моделей. Изменения схемы требуют ADR.
3. В рабочем дереве из архива много файлов выглядят измененными из-за `CRLF/LF`, хотя по содержанию почти все изменения не смысловые.
4. Нет тестовой папки; есть только ручные сценарии проверки.
5. В архиве есть `.env`, локальные базы, backup-папки, `.pyc`, `venv_trailers/`; их нельзя давать Cursor как основной контекст.
6. `requirements.txt` выглядит раздутым и может содержать лишние зависимости из глобального окружения.
7. `app.py` содержит hardcoded `SECRET_KEY = 'dev-secret-key-change-me'` и жесткую привязку к `trailers.db`; перед production-стабилизацией это нужно вынести в environment/config.
8. README_CHANGELOG может быть частично устаревшим: там указан старый migration head `c5d2e8f1a9b0`, а фактический migration head в архиве — `f1a2b3c4d5e6`.

## Частые ошибки AI в этом проекте

Добавлять сюда каждый повторяющийся сбой Cursor/AI. Уже известные риски:

- начинает менять код без research/plan;
- путает шапку заказа и строки заказа;
- делает order-level логику там, где уже нужна line-level логика;
- смешивает юридическую продажу и физическую отгрузку;
- считает `SOLD` финальным складским состоянием;
- предлагает свободный VIN, который уже существует у прицепа;
- смешивает роли менеджера, логиста, производства и кладовщика;
- меняет большие файлы целиком из-за форматирования/переносов строк;
- трогает миграции без проверки текущей версии базы;
- добавляет зависимости вместо локального решения;
- использует backup-файлы как актуальный код;
- пытается строить налоговый/финансовый модуль без отдельного проектирования.
