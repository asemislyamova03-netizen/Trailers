# Контракт связи «продано из выпущенных»

Дата: 2026-09-29  
Статус: research/design only. Показатель остаётся `BLOCKED`.  
База: `6896037c391b32210935604fd3db866d71e4d7fd`  
Код, миграция, отчёт, живая БД и сервер в этом шаге не меняются.

Документ описывает фактические маршруты на этом SHA и минимальный контракт на будущее. Исторические строки сами не достраиваются: backfill через `trailer_id` запрещён.

## Вывод

Сейчас одну единицу выпуска нельзя однозначно назвать проданной.

Цепочка в данных такая:

`ProducedUnit` → необязательный `trailer_id` → `Trailer` ← необязательный `trailer_id` ← `SalesRealizationLine` → `SalesRealization`

Ни на одном звене нет ключа «эта строка реализации продала именно эту единицу». Совпадение `trailer_id` таким ключом не является: колонка у единицы не уникальна, после смены она пустая, а продажа ищется по прицепу, не по выпуску.

Пока колонки связи нет и правило её заполнения не принято, отчёт не считает число. Константа `SOLD_FROM_PRODUCED` в `shift_director_report.py` остаётся как есть.

## Что смотрел

| Место | Факт на этом SHA |
|---|---|
| `models.py` `ProducedUnit` | `trailer_id` nullable, индекс не unique. Unique только `(shift_output_id, unit_seq)`. |
| `models.py` `SalesRealization` / `SalesRealizationLine` | У строки есть `trailer_id`, `order_line_id`, `vin_registry_id`. `produced_unit_id` нет. |
| `models.py` `VinRegistry` | `produced_unit_id` нет. Колонка снята миграцией `e5b8c7d9a012`. |
| `models.py` `InventoryOperation.produced_unit_id` | Связь списания материалов старого `+1`, не продажи. |
| `shift_posting.py` `_create_produced_units` | Смена создаёт единицу без прицепа, статус `produced_no_vin`. |
| `views.py` `logistics_assign_vin` | Живой маршрут VIN: создаёт новый `Trailer` и пишет `unit.trailer_id`. |
| `views.py` `sales_realization_post` / `sales_realization_delete` | Проведение и откат продажи. Отдельного документа возврата нет. |
| `tests/test_shift_director_report.py` `test_sold_from_produced_stays_blocked_when_trailer_matches_realization` | Совпадение прицепа со строкой реализации не даёт число. |

## Фактический маршрут

### 1. Выпуск прицепа сменой

`shift_posting.py` `post_shift` для `Item.item_type == 'TRAILER'` вызывает `_create_produced_units`.

Единица получает заявку, номенклатуру, склад назначения, `shift_output_id`, `unit_seq`, `status='produced_no_vin'`. `trailer_id` не заполняется.

Деталь (`COMPONENT`) в `ProducedUnit` не превращается: по ней пишется приход на склад (`apply_shift_component_receipt`). Это другой контур, не продажа единицы выпуска.

Сверхплановые прицепы тоже становятся `ProducedUnit`, но через строку пополнения склада, без заказа покупателя.

### 2. Старый `+1`

`views.py` `production_line_produce_one`, маршрут `POST /production/lines/<id>/produce-one`.

Создаёт `ProducedUnit` без `shift_output_id`, без прицепа, статус `produced_no_vin`. Материалы списывает `apply_production_consumption` и кладёт `InventoryOperation.produced_unit_id`.

`shift_posting.py` `plus_one_blocked_reason` запрещает `+1`, если зона в режиме только смен или по заявке уже есть выпуск проведённой смены. Обратного запрета нет: смена может пройти по заявке, где раньше уже был `+1`. Это разные строки `ProducedUnit`.

### 3. Закрепление за заказом ещё без VIN

`POST /orders/<order_id>/lines/<line_id>/attach-produced-unit/<unit_id>` вызывает `_attach_produced_unit_to_order_line`.

Пишутся `order_id` и `order_line_id`. Прицеп и реализация не создаются. Одна строка заказа с количеством N может держать несколько единиц. `order_line_id` поэтому не ключ продажи одной единицы.

### 4. VIN и прицеп

Живой маршрут: `GET/POST /logistics/produced-units/<unit_id>/assign-vin` (`logistics_assign_vin`).

Условия входа: `unit.status == 'produced_no_vin'`. Берётся свободный или зарезервированный полный VIN без прицепа. Если такой VIN уже есть у `Trailer`, новый прицеп не создаётся.

Иначе создаётся новый `Trailer`, затем:

- `unit.status = 'vin_assigned'`
- `unit.trailer_id = trailer.id`
- `vin_registry.trailer_id = trailer.id`, статус VIN `confirmed`
- строке заказа пишется тот же `trailer_id`

Если по заказу уже выданы документы или статус `sold_not_shipped`, прицеп сразу становится `SOLD`. Это побочный статус прицепа, не документ реализации.

`_attach_produced_unit_to_existing_trailer` тоже умеет записать `unit.trailer_id` на уже существующий прицеп и отказывает, если у прицепа уже есть другая единица. На этом SHA у функции нет вызова. На неё нельзя опираться как на живой маршрут.

`vin_registry_assign` (`POST /logistics/vin-registry/<id>/assign`) вешает VIN на уже существующий прицеп и не читает `ProducedUnit`. После этого прицеп может продаться, а единица выпуска останется со своим или пустым `trailer_id`.

`ProducedUnit.trailer` объявлен как один объект (`uselist=False`). В базе unique на `produced_unit.trailer_id` нет: индекс `ix_produced_unit_trailer_id` создан с `unique=False` (`8b1f4a9d2c70`). Код уже готов к нескольким единицам на одном прицепе: `_trailer_production_context` берёт первый элемент списка, а смена комплектации читает все `ProducedUnit` с этим `trailer_id`.

### 5. Черновик реализации

`POST /orders/<order_id>/realizations/new` → `_build_sales_realization_from_order`.

Для техники строка реализации появляется только если у строки заказа хватает активных VIN с физическим прицепом (`_resolve_realization_trailer_units_for_line`). Каждая пара `(Trailer, VinRegistry)` даёт отдельную строку:

- `line_type='trailer'`
- `inventory_effect='trailer_unit'`
- `quantity=1`
- `trailer_id`, `vin_registry_id`, `order_line_id`, `vin_full`

`produced_unit_id` не пишется. Комплектующие идут отдельной строкой `inventory_effect='ship_from_stock'` без прицепа и без единицы выпуска.

Пока есть черновик по заказу, второй черновик не создаётся. Черновик продажей не является.

### 6. Проведение

`POST /realizations/<id>/post` (`sales_realization_post`).

Проводится только `draft`. Повторно провести тот же документ нельзя. Для `trailer_unit` проведение отвергается, если `_posted_realization_for_trailer` уже нашёл другую проведённую строку с тем же `trailer_id` и `inventory_effect='trailer_unit'`. Это проверка в коде через `.first()`, не ограничение базы. Две проведённые строки на один прицеп можно вставить в обход экрана.

После успеха: `status='posted'`, `posted_at=utcnow()`. `_apply_realization_shipment_effect` ставит прицепу `status='SOLD'` и `lifecycle_status='customer_shipped'`. Единицу выпуска проведение не обновляет.

Дата документа `realization_date` задаётся при создании (сегодня) и меняется в `sales_realization_edit` даже у проведённой реализации. `posted_at` форма редактирования не трогает.

`order.realized_at` — это максимум `posted_at` по заказу, и только когда реализованы все строки заказа. Для одной единицы это чужой уровень.

### 7. Отмена, возврат, повтор

Отдельной модели возврата нет. Поля `SalesRealization.cancelled_at`, `cancelled_by_user_id`, `cancel_reason` в `views.py` нигде не заполняются. Статус `cancelled` для реализации не выставляется.

Откат — удаление: `POST /realizations/<id>/delete`.

- Черновик удаляется без складского эффекта.
- Проведённую удаляют директор или админ.
- Перед удалением `_revert_realization_shipment_effect` возвращает статус прицепа, если другой проведённой строки по этому `trailer_id` нет.
- Затем `db.session.delete(realization)`. Строки уходят каскадом `delete-orphan`.

После удаления строки нет. Повторить продажу можно новым черновиком и новым проведением того же прицепа. Старый документ не сохраняется, даты возврата нет. «Был продан, потом возвращён» из текущих таблиц не восстановить.

## Почему текущие ключи не годятся

| Кандидат | Почему не ключ продажи единицы |
|---|---|
| `SalesRealizationLine.trailer_id = ProducedUnit.trailer_id` | У единицы поле пустое до VIN и не unique. У прицепа может не быть единицы (склад, импорт) или быть несколько. Продажа уже проведённого прицепа не доказывает, что продана именно эта единица. |
| `VinRegistry.produced_unit_id` | Колонки нет с миграции `e5b8c7d9a012`. |
| `VinRegistry.trailer_id` | Связь VIN с прицепом. До единицы выпуска не доходит. |
| `order_line_id` | Одна позиция заказа — несколько единиц и несколько строк реализации. Закрепление выпуска пишет заказ без продажи. |
| `Trailer.status == 'SOLD'` | Ставится проведением, а также присвоением VIN при уже выданных документах и другими маршрутами. Даты продажи у прицепа нет. |
| `InventoryOperation.produced_unit_id` | Списание материалов `+1`, не реализация. |
| `CustomerOrder.realization_status` / `realized_at` | Статус всего заказа, не одной единицы. |

## Минимальный контракт на будущее

Это правило для отдельного решения. В этом шаге колонка не добавляется и отчёт не начинает считать.

### Ключ

`sales_realization_line.produced_unit_id` — nullable внешний ключ на `produced_unit.id`.

Связь живёт на строке реализации, не на единице и не в VIN-реестре:

- у одного документа несколько строк (количество N и чужие комплектующие);
- у одной единицы со временем может быть несколько строк, если документ удалили и провели новый;
- VIN-реестр эту связь уже сознательно потерял.

Одна строка указывает не больше чем на одну единицу. Комплектующие (`inventory_effect != 'trailer_unit'`) ключ не получают.

### Когда пишется

Только в `sales_realization_post`, в той же транзакции, что и `status='posted'`. В черновике ключ пустой: черновик ещё не продажа, строки черновика можно удалить.

Для строки с `inventory_effect='trailer_unit'` и заполненным `trailer_id` смотрим единицы с этим `trailer_id`.

Пишем id единицы только если одновременно:

1. такая единица ровно одна;
2. её `status='vin_assigned'`;
3. её `item_id` совпадает с `item_id` строки (и с прицепом);
4. у строки `quantity` соответствует одной штуке, как это уже делает сборщик реализации.

Если единиц ноль — оставляем `NULL`. Это продажа склада или прицепа без выпуска. В числитель «из выпущенных» она не входит. Ошибкой проведения это не делаем: иначе встанет обычная продажа из наличия.

Если единиц две и больше — id не выбираем «первую» и не пишем. Такое проведение нельзя закрывать догадкой. Поведение экрана (отказать в проведении или провести строку без ключа) — решение HQ ниже. До решения отчёт остаётся `BLOCKED`.

Ключ не пишется задним числом для уже проведённых строк. Совпадение прицепа в старых данных не заполняется.

Поздняя привязка единицы к прицепу, который уже продан, ключ тоже не создаёт: запись бывает только в момент проведения. Пока нет нового проведения, такая единица не продана из выпуска.

### Уникальность

Среди строк, у которых документ `posted` и `inventory_effect='trailer_unit'`, один `produced_unit_id` встречается не больше одного раза.

Пока первая проведённая строка существует, второе проведение того же прицепа уже отвергает `_posted_realization_for_trailer`. Этого мало: в базе уникальности нет. Будущая проверка должна смотреть и на `produced_unit_id`, не только на `trailer_id`.

Unique на `produced_unit.trailer_id` в минимальный контракт не входит. Сначала нужен отдельный просмотр дублей только чтением. Пока дубли возможны, правило «ровно одна единица» как раз и отказывается считать.

### Что считать проданным

Единица продана сейчас, если есть ровно одна строка:

- `produced_unit_id` равен этой единице;
- родительский `SalesRealization.status == 'posted'`;
- `inventory_effect == 'trailer_unit'`.

Черновик, удалённый документ, статус прицепа `SOLD` без такой строки и строка комплектующей не считаются.

Для карточки смен в числитель входят только единицы с непустым `shift_output_id`, у которых смена `posted`. Старый `+1` (`shift_output_id` пустой) в это число не прибавляется. Если его понадобится показать, это отдельный ряд, не сумма с сменами.

Знаменатель «выпущено» этот документ не переопределяет. Его уже считает отчёт смен по проведённым сменам. Выпуск без VIN в числитель продажи не попадает: строки реализации без прицепа и VIN для техники не собираются.

### Дата и статус

Зерно учёта — строка реализации, не заказ.

Два уже существующих поля даты:

- `realization_date` — дата документа. Ею уже фильтрует директорский отчёт реализаций (`realization_report_records`). Её можно изменить после проведения, и единица переедет в другой период.
- `posted_at` — момент проведения. Форма редактирования его не меняет.

Пока HQ не выберет одно поле, период не считается. `order.realized_at` и отсутствие даты у `Trailer.status` не используются.

Статус продажи для показателя — только `posted` у документа плюс условия строки выше. `draft` не продажа. Колонки `cancelled_*` сейчас пустые по коду и статусом возврата не являются.

### Обратные операции

Текущий откат — удаление проведённого документа. Строка и будущий ключ исчезают вместе с ней. Повторное проведение создаёт новую строку и, по контракту, новый ключ на ту же единицу, если на прицепе по-прежнему ровно одна подходящая единица.

Это отвечает на вопрос «продана ли единица сейчас». Это не отвечает на вопрос «была продажа и возврат в другом периоде»: старой строки уже нет, отдельного документа возврата нет.

Пока откат остаётся физическим удалением, показатель может быть только снимком текущих проведённых строк. История возвратов — отдельное решение HQ, не додуманный статус `cancelled`.

## Что остаётся BLOCKED до решения HQ

Показатель на экране и в ответе `build_shift_director_report` остаётся `status='BLOCKED'`, `value=None`. Число не подставляется.

1. **Принять сам ключ.** Nullable `sales_realization_line.produced_unit_id`, запись только при проведении и только при ровно одной подходящей единице. Без этой колонки считать нечего.
2. **Неоднозначный прицеп при новом проведении.** Две и больше единицы на одном `trailer_id`: отказать в проведении этой строки или провести её без ключа. До выбора такие строки не дают цифру. Продажа без единицы (ноль `ProducedUnit`) ключ не получает и в числитель не входит — это не развилка, это граница показателя.
3. **Дата периода.** `realization_date` или `posted_at`. Оба поля уже есть, смысл разный, потому что дату документа можно поменять после проведения.
4. **Срез периода.** Продано в периоде, выпущено в периоде или пересечение. Этот документ срез не выбирает.
5. **Возврат как событие.** Сейчас откат удаляет документ. Снимок «сейчас проведено» из контракта следует. История «продажа минус возврат» требует отдельного статуса или документа возврата. Выдумывать `cancelled` из пустых колонок нельзя.
6. **Старый `+1`.** В числитель смен не входит. Нужен ли отдельный ряд — отдельное да или нет. Суммировать со сменами нельзя.
7. **Детали.** Продажа `COMPONENT` не является продажей `ProducedUnit`. В этот показатель не входит.
8. **Backfill.** Старые проведённые строки по совпадению `trailer_id` не заполняются. Иначе в цифру попадут склад, дубли прицепа и прицеп, который стал `SOLD` до связи с выпуском.
9. **Unique на `produced_unit.trailer_id`.** Не часть минимального ключа. Только после отдельного просмотра дублей, без правки остатков и без инвентаризации.

## Что этим шагом не делается

- Нет миграции и нет нового поля.
- `shift_director_report.py`, `views.py` и шаблон отчёта не меняются.
- Нет скрипта, который проставляет связь по живым или старым строкам.
- Нет правки остатков, зон, учёта направлений и инвентаризации.
- Нет PR, merge и deploy.
