2. Проверить на сервере `/orders/<id>/edit` для заказа со строками: форма показывает только шапку и справочный список позиций, без выбора VIN/прицепа/источника.

6. Проверить блокировки: если производство начато, есть договор, документы, реализация, отгрузка или перемещение, смена источника показывает понятную причину и не меняет данные.
7. Проверить `/orders`: один основной статус, главный блокер, следующее действие и фильтры по состояниям сделки.

9. Проверить `/logistics/vin-registry`: активный фильтр должен отличаться заголовком, а загрузка VIN должна быть только в раскрываемом блоке `Загрузка VIN`.
10. Проверить `/production/workspace` на телефоне: задания и выпуск должны быть компактными строками.
11. На сервере повторно открыть роли в браузере: менеджер, логист, производство, директор; визуально проверить меню, кнопки перемещений и активные VIN-фильтры.
12. Проверить, что нужный прицеп с производственного склада появился в перемещении и в создании заказа; в перемещении выбрать его из таблицы доступных VIN.
13. Проверить `/stock-movements/new`: новая клиентская отгрузка не создаётся отдельным перемещением, выдача клиенту закрывается проведением реализации.
14. Проверить проблемный заказ `ORD-000035`: если у строки есть прицеп с VIN, но нет активного VIN-реестра по строке, нажать `Создать связь VIN`, затем создать реализацию заново.
15. Удалить ошибочную реализацию с чужим VIN и создать реализацию заново по тому же заказу.

21. Не переходить к BOM/1С/ИИ/закупкам, пока безопасное редактирование заказа из Итерации 1 не принято.

- Утвердить классификацию групп конфигуратора: какие G-группы являются грузовыми автомобилями, а какие остаются прицепами/зерновозами.
- Объяснить пользователям новый порядок: перед отгрузкой нужна проведённая `Реализация товаров и услуг`.
- Определить хостинг организации, где будет проверяться Kaspi, и кто отвечает за доступы/домен/env-переменные.
- Подтвердить новую модель производства: участки, склады комплектующих/полуфабрикатов, сотрудники, смены и результаты месяца для директора.
- Уточнить правила для разных шаблонов договоров по группам/ОТТС/модификациям и будущие этапы оплат.
- Заполнить первые реальные правила `contract_template` для грузовых и легковых договоров.
- Уточнить сценарий Kaspi: это импорт заказов магазина, платежные ссылки/QR, статусы оплат или всё вместе.
- После проверки первого импорта Kaspi решить, нужен ли автоматический фоновый sync новых заказов или пока достаточно ручного импорта по номеру заказа.
- Спроектировать справочник соответствий `артикул Kaspi -> наша номенклатура`, потому что артикулы магазина могут отличаться от внутренних артикулов CRM.
- Спроектировать безопасный механизм замены ответственного лица по заказам/договорам и команду связки исторического договора с созданным задним числом заказом.
- Спроектировать учет запчастей/комплектов без VIN: продажа, склад, отчетность, связь с заказом и договором без прицепного жизненного цикла.

## Что нельзя забыть

- Не смешивать trailers с clinic app и flexity admin.
- Цены по конфигурации могут быть не заполнены и не должны блокировать заказ.
- Источник выбора параметров конфигуратора - матрица допустимости, а не справочник номенклатуры и не ценовые матрицы.
- Разные прицепы в одном заказе должны жить как разные строки заказа, а не как количество одной строки.
- Выдача документов и отгрузка должны проверяться по строкам заказа, иначе один VIN может ошибочно закрыть весь заказ.
- Удаление заказа должно оставаться безопасным: нельзя удалять заказ, если уже есть резервы, VIN, договор, оплаты, производство, перемещения, документы или отгрузка.
- Токен Kaspi нельзя коммитить в репозиторий; хранить только в переменных окружения или закрытых настройках сервера.
- Текущий сервер не получает ответ от `kaspi.kz`; проверку Kaspi продолжать на хостинге организации или другом IP.
- Kaspi и будущий WhatsApp должны попадать в общий контур `Lead`/`LeadMessage`, чтобы менеджер видел их в диалогах, а не в отдельном изолированном разделе.
- Отчеты для менеджера должны оставаться ограничены его складом/назначенными заказами.
- Для исторических отчетов источник выручки должен быть договор/продажа с датой и суммой, а не просто VIN в остатках.
- Исправления конкретных импортированных договоров по артикулам выполняются вручную пользователем, если это бизнес-корректировка данных.
- Для исправления директорских отчетов по историческим договорам использовать отчетные поля договора `warehouse_id` и `assigned_user_id`, не менять фактический склад прицепа без отдельного запроса.
- Исторические заказы можно создавать задним числом; связку с уже существующим договором делать отдельной проверяемой командой, чтобы не сломать договор/VIN.
- Комплекты запасных частей нельзя бездумно проводить как прицепы: нужен отдельный контур для номенклатуры без VIN.
- У производственника в левом меню не должно быть нескольких активных пунктов на одном экране.
- Выручка в новой модели должна считаться по проведённым реализациям, а договор/документы АвтоЦОНа остаются юридическим оформлением прицепа.
- Старую кнопку `Комплектация` нельзя оставлять как простую смену `item_id`; следующий шаг - перевод на складскую операцию с BOM и остатками.
