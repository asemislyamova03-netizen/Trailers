## Что уже реализовано

- Базовая структура проектного контекста и planning-документов.
- Исправлена обработка конфигуратора при переводе/сохранении заказа в производство через форму редактирования.
- Форма заказа в производство переведена на общую логику конфигуратора: доступные параметры фильтруются по матрице допустимости, ОТТС/VIN показывают ошибки конфигурации явно.
- В справочнике ОТТС/VIN-модификаций номер и модификация ОТТС выбираются из активного справочника ОТТС, а не вводятся свободным текстом.
- В справочнике групп номер ОТТС выбирается из активного справочника ОТТС.
- В подборе прицепа спецпараметры выводятся из матрицы допустимости; ценовые матрицы не скрывают допустимые параметры.
- В подборе прицепа списки параметров динамически обновляются после выбора группы/параметров и синхронизируют hidden-поля действий.
- Конфигуратор больше не подставляет `NOOK` и `NONE` автоматически, если опорное колесо или тент не выбраны.
- Поиск ОТТС/VIN-модификации учитывает выбранную высоту борта для любых типов кузова, включая `GRAINTRAILER`.
- Заказ в производство поддерживает количество больше 1 для одной конфигурации: сумма от конфигуратора умножается на количество, производственная потребность синхронизируется по количеству.
- Добавлена основа для многострочных заказов и договоров: `CustomerOrderLine`, `SalesContractLine`, привязка VIN/резервов/производства к строке заказа.
- Добавлена основа производственного модуля: участки/цеха, сотрудники производства, смены, результаты смен, спецификации номенклатуры, склады комплектующих и полуфабрикатов.
- Менеджерам открыт раздел производства и перемещения; у логиста в навигации оставлен простой логистический контур и реестр VIN.
- Запуск потребностей в производство перенесён к менеджеру: менеджер видит новые потребности своего склада и отдаёт их в производство.
- Логистический контур для роли логиста сужен до реестра VIN; рабочий стол логиста перенаправляет логиста в VIN-реестр, чтобы он не запускал производство, не резервировал/привязывал VIN и не выполнял менеджерские операции.
- Менеджер может привязать VIN к выпущенной единице из своего производственного блока; фактический выпуск изделия остаётся доступен только производственникам.
- Менеджер может отправить готовый прицеп со склада выпуска на свой склад из вкладки готовых к отправке прицепов; действие доступно только если склад назначения совпадает со складом менеджера.
- Реестр VIN для логиста сортируется по порядковому номеру VIN: сверху отображается самый большой `serial7`, а не последняя внесённая запись.
- Менеджеру открыто изменение комплектации прицепа и выпущенной единицы без VIN; пустые опциональные параметры не должны автоматически превращаться в тент/каркас 90 или опорное колесо.
- Проверка изменения комплектации больше не считает смену высоты борта сменой размера рамы/кузова: база сравнивается по группе, коду размера кузова и количеству осей.
- Реестр VIN адаптирован для работы логиста с телефона: кнопка `Открыть` находится рядом с VIN, второстепенные колонки скрываются на малых экранах.
- Администратору добавлена корректировка и удаление ошибочно созданных VIN на начальном этапе.
- В карточке заказа добавлен блок позиций: можно добавить отдельную позицию из наличия с резервом VIN или позицию в производство с созданием потребности; сумма заказа пересчитывается по строкам.
- В карточке заказа добавлено безопасное управление позициями до выдачи документов: редактирование количества/цены/комментария и удаление строки без резервов, VIN, производства, перемещений, договора и других связанных операций.
- Подбор прицепа можно открыть из существующего заказа и добавить другую конфигурацию отдельной строкой: из наличия резервируется выбранный VIN, для производства создаётся новая позиция и `SupplyNeed` по выбранной конфигурации.
- Администратору добавлено безопасное удаление заказа: удаление блокируется, если есть договор, оплаты, резервы, VIN, производство, перемещения, выпуск, документы или отгрузка.
- Администратор больше не направляется на панель директора: стартовая страница и первый пункт меню ведут в `Заказы`; также добавлен вход в `Договоры`.
- При создании договора из заказа создаются строки договора по строкам заказа, а печатная спецификация выводит несколько позиций.
- Выдача документов по заказу проверяет VIN по строкам заказа: для каждой trailer-позиции должно хватать привязанных VIN.
- Физическая отгрузка добавлена по строкам заказа: каждая строка закрывается отдельно, заказ считается отгруженным после отгрузки всех строк.
- Для печати/PDF договора добавлен выбор активного шаблона из `ContractTemplate` по группе, ОТТС, модификации, исполнению и типу клиента; если подходящего файла шаблона нет, используется текущий `contract_print.html`.
- Менеджеру, директору и логисту добавлен раздел `Отчеты`: продажи, динамика, филиалы, типы прицепов, оборачиваемость склада, склад, производство, перемещения, проблемы и финансы.
- Добавлен интерфейс `Шаблоны договоров`: директор/админ может создавать правила выбора шаблона, а в карточке заказа видно, какой шаблон применится к договору.
- Директорские отчеты по продажам/динамике/филиалам/типам/оборачиваемости переведены на агрегированные показатели и графики без портянки заказов.
- Источник продаж в отчетах расширен до `SalesContract`: исторические договоры/продажи, загруженные из Excel без CRM-заказа, учитываются в выручке, количестве, динамике, филиалах, типах и оборачиваемости.
- В отчетах добавлен фильтр направления: все, легковые, грузовые/спец, без VIN/прочее; договоры без VIN/артикула или с суммой от 3 млн ₸ показываются предупреждением как потенциальные искажения.
- В меню производственника убраны дублирующие пункты, которые подсвечивались одновременно; навигация по заданиям осталась вкладками внутри экрана производства.
- Добавлен первый безопасный слой интеграции Kaspi Магазина: импорт заказа Kaspi по коду или списком за период/состояние в заявку `Lead` и входящее сообщение `LeadMessage` без хранения токена в коде.
- Для исторических договоров без CRM-заказа добавляется отчетная атрибуция: склад и ответственный могут храниться прямо в `SalesContract` и использоваться в директорских отчетах без изменения фактического склада прицепа.

## Что требует проверки

- Актуальное состояние серверной версии после последних git pull и перезапусков.
- Создание или редактирование заказа с новой конфигурацией прицепа и источником обеспечения `production`, включая сценарий без заполненной цены.
- Заполнение строк ОТТС/VIN-модификаций через выбор действующего ОТТС из списка.
- Выбор группы `006G` на сервере: если в матрице допустимости стоят флажки для высоты борта и SINGLE/DOUBLE, эти параметры должны отображаться в заказе и подборе.
- Проверить, что для грузовых групп без флажка опорного колеса поле опорного колеса остаётся пустым/без вариантов.
- Проверить на сервере `006G + GRAINTRAILER + E150 + DOUBLE`: строка ОТТС есть, после обновления должна подтянуть VIN-модификация `000011`.
- Проверить создание/редактирование производственного заказа с количеством 2 и одной конфигурацией.
- Проверить добавление двух разных конфигураций в один заказ через карточку заказа → подбор прицепа.
- Проверить удаление админом пустого тестового заказа и блокировку удаления заказа с резервом/VIN/оплатой/договором.
- Проверить, что менеджер видит новые потребности и может отдать их в производство, а логист больше не видит этот блок.
- Проверить, что менеджер может открыть выпущенную единицу без VIN и привязать VIN, а производственные кнопки выпуска для менеджера неактивны.
- Проверить, что менеджер видит кнопку `Переместить на мой склад` для готового прицепа со своим складом назначения и после нажатия получает входящее перемещение.
- Проверить в реестре VIN у логиста, что сверху показывается последний VIN по порядковому номеру, а не по дате внесения.
- Проверить на сервере изменение комплектации у менеджера: смена борта, тента и опорного колеса не должна менять группу/кузов/размер рамы и не должна подставлять `90` при пустом тенте.
- Проверить производство и реестр VIN на смартфоне после серверного обновления; локальная browser-проверка в Codex не запустилась из-за ошибки доступа runtime.
- Проверить раздел `Отчеты` под ролями manager/director/logistics на серверных данных: продажи, динамика, филиалы, типы прицепов и оборачиваемость склада.
- Проверить, что исторические Excel-продажи есть именно в `SalesContract`; если Excel загрузил только VIN/остатки без договора, для выручки нужны дата продажи и сумма.
- Проверить выбор шаблона договора после заполнения `contract_template`: fallback должен оставлять текущий печатный договор рабочим.
- Проверить, что у производственника слева активен только один пункт `Производство`.
- Интеграция Kaspi требует проверки API/формата данных и безопасного хранения токена; токен нельзя хранить в коде.
- Проверить на сервере переменную окружения `KASPI_SHOP_TOKEN` и импорт реального заказа Kaspi через раздел `Kaspi`.
- Артикулы Kaspi могут отличаться от внутренней номенклатуры; сейчас точное совпадение используется только как подсказка, а полноценный справочник соответствий ещё не реализован.
- Проверить на сервере корректировку исторических крупных договоров: суммы 18,8 млн, 18 млн, 14 млн и 8,5 млн должны попадать в директорских отчетах на склад грузовых прицепов и ответственного Кальмана Игоря.

## Главный фокус сейчас

- Стабилизировать сценарии заказов, производства, номенклатуры и VIN в trailers; следующий инфраструктурный фокус - проверить Kaspi на хостинге организации, потому что текущий сервер не получает ответ от `kaspi.kz`.

## Риски

- Не смешать бизнес-логику trailers с другими проектами.
- При неверной обработке конфигуратора заказ может сохраниться без ОТТС/VIN-модификации, что ломает дальнейшую VIN-логику.
- Незаведённые цены допустимы, поэтому отсутствие цены должно оставаться предупреждением, а не блокировкой.
- Полный пользовательский сценарий двух разных прицепов в одном заказе реализован частично: добавление, безопасное редактирование/удаление строк и построчная отгрузка есть, но ещё нужно проверить привязку VIN к производственной строке на серверных данных.
- Автоматическое списание комплектующих/полуфабрикатов по спецификации ещё не включено в бизнес-операции выпуска.
- Текущий сервер/IP не подходит для проверки Kaspi API: `google.com` отвечает, а `kaspi.kz` уходит в timeout. Нужна проверка на хостинге организации или другом IP.
